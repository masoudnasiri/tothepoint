# راهنمای UAT کسب‌وکاری فاز ۱۲ (پس از بازطراحی UI)

این راهنما برای کاربر غیرتوسعه‌دهنده تهیه شده است تا **تست پذیرش کاربری** روی نسخه `Rivar 1.0.0-rc1` انجام شود.

## هدف این دور تست

- تایید کاربری/بصری سیستم بعد از بازطراحی رابط کاربری
- بررسی آمادگی جریان‌های عملیاتی با دیتاست واقعی UAT
- ثبت دقیق مشکلات برای رفع قبل از انتشار نهایی

## اطلاعات نسخه و هویت محصول

- Product: `Rivar`
- Producer: `Corbit`
- Version: `1.0.0-rc1`

## اطلاعات ورود (محیط UAT)

- آدرس محیط UAT را از تیم فنی دریافت کنید.
- کاربر نمونه: `admin`
- اگر رمز عبور شما متفاوت است از مسئول استقرار بگیرید.

## دامنه دیتاست UAT

- 100 قلم Master Item
- 10 پروژه
- 500 آیتم پروژه
- 40 تامین‌کننده تاییدشده (20 داخلی + 20 خارجی)
- بودجه ماهانه از تیر تا اسفند 1405
- پوشش متنوع پکیج/ساب‌آیتم و اختلاف زمان تحویل (زودتر/هم‌زمان/دیرتر)
- **Optimization از قبل اجرا نشده** و باید توسط کاربر در صورت نیاز انجام شود.

## موارد خارج از این دور تست

- توسعه قابلیت جدید
- تست فشار/کارایی سطح زیرساخت
- تست نفوذ امنیتی
- تغییر در مدل داده یا اسکیما

## تعریف شدت خطا

- **Blocker**: جریان کلیدی متوقف می‌شود و راه‌حل جایگزین ندارد.
- **Major**: جریان اصلی با اختلال جدی، ولی با workaround محدود قابل ادامه است.
- **Minor**: مشکل عملکردی/نمایشی با اثر محدود.
- **Cosmetic**: فقط ظاهری/متنی، بدون اثر روی منطق.

   - نمایش نام `Rivar`، `Corbit` و نسخه `1.0.0-rc1`

5. **صفحه Procurement**
   - اقلام نهایی‌شده در مسیر تامین قابل مشاهده باشند

7. **بررسی وضعیت پوشش پکیج**
   - وضعیت Fully Covered و Partially Covered قابل مشاهده باشد
   - کمبود پوشش ساب‌آیتم‌ها قابل تشخیص باشد

8. **بررسی اختلاف زمان تحویل**

   - خروجی تصمیم‌ها قابل مشاهده و قابل تحلیل باشد

14. **جریان Invoice/Payment**
   - صفحات مالی مرتبط بدون خطای blocker قابل استفاده باشند

15. **گزارش‌ها/داشبورد/ممیزی پس از اقدامات کاربر**
   - اثر اقدامات کاربر در گزارش‌ها منعکس شود

## قواعد تفسیر جریان نقدینگی در فاز 12B

قبل از اجرای Optimization و قبل از LOCK شدن تصمیم‌ها:

- بودجه ماهانه باید دیده شود (به‌عنوان ظرفیت/بودجه)
- `Forecast Inflow` باید صفر باشد مگر برنامه وصول تاییدشده وجود داشته باشد
- `Forecast Outflow` باید صفر باشد مگر برنامه پرداخت تامین‌کننده تاییدشده وجود داشته باشد
- `Actual Inflow/Outflow` باید صفر باشد مگر پرداخت/دریافت واقعی ثبت شده باشد
- قیمت فروش آیتم پروژه و گزینه‌های تامین انتخاب‌نشده نباید وارد forecast/actual شوند

بعد از LOCK شدن تصمیم و ثبت برنامه زمانی:

- Forecastها باید بر اساس schedule تاییدشده ظاهر شوند

بعد از ثبت رخداد مالی واقعی:

- Actualها باید فقط از همان رخدادهای واقعی (پرداخت/دریافت) محاسبه شوند

## سناریوهای الزامی فاز 12C (Procurement Package Finalization Gate)

1. **نهایی‌سازی پکیج**
   - هنگام فعال‌کردن `Mark as finalized`، وضعیت پکیج در لیست باید `Finalized` نمایش داده شود.
   - پکیج Draft نباید قابل ارسال به Optimization باشد.

2. **ارسال تک‌آیتم به Optimization**
   - اگر پوشش کامل باشد، ارسال مستقیم انجام شود.
   - اگر پوشش ناقص باشد، پیام هشدار کمبود نمایش داده شود و بدون تایید صریح کاربر ارسال نشود.

3. **ارسال گروهی پکیج‌های نهایی**
   - گزینه `Send all finalized packages to optimization` باید فعال باشد.
   - آیتم‌های کامل ارسال شوند؛ آیتم‌های ناقص فقط با تایید صریح ارسال شوند؛ آیتم‌های already sent/skip مشخص باشند.

4. **قفل‌گذاری پس از ارسال**
   - آیتم ارسال‌شده باید `sent to optimization` شود.
   - دکمه‌های create/edit/delete پکیج برای آن آیتم غیرفعال شوند.
   - در صورت rollback امن، امکان ویرایش مجدد بازگردد.

5. **فیلترهای جدید صفحه Procurement**
   - فیلتر وضعیت Optimization: `all / not sent / sent / rolled back`
   - فیلتر وضعیت پوشش: `all / no package / partial / full / over-covered / missing components`

6. **وضوح معنای Coverage**
   - تمایز بین `This package coverage` و `Aggregate/Optimization-eligible coverage` مشخص باشد.
   - مقادیر بیش از 100% به‌صورت surplus/over-coverage نمایش داده شوند، نه صرفا full.

## سناریوهای الزامی فاز 12D (Bulk Rollback from Optimization)

1. **دکمه بازگردانی گروهی**
   - در صفحه Procurement، دکمه `Rollback from optimization / بازگردانی از بهینه‌سازی` هنگام وجود آیتم Sent نمایش داده شود.
   - اگر آیتم rollbackable موجود نباشد، وضعیت غیرفعال/اطلاع‌رسانی مناسب دیده شود.

2. **دیالوگ پیش‌نمایش بازگردانی**
   - فیلترهای چک‌باکسی (نوع پکیج، پوشش، نوع تامین‌کننده، تک/چند تامین‌کننده، ارسال ناقص تاییدشده) قابل انتخاب باشند.
   - فیلتر بازه هزینه `IRR` (حداقل/حداکثر) و فیلتر بازه تاریخ (`from/to`) قابل اعمال باشند.
   - انتخاب فیلد تاریخ (`sent date / delivery / purchase / need date`) در UI قابل تغییر باشد.

3. **خروجی پیش‌نمایش**
   - شمارنده‌های `matched / rollbackable / unsafe` نمایش داده شوند.
   - آیتم‌های unsafe با دلیل رد شدن نمایش داده شوند.
   - هشدار واضح درباره unlock شدن ویرایش پکیج پس از rollback وجود داشته باشد.

4. **اجرای بازگردانی با تایید صریح**
   - بدون تایید صریح، rollback اجرا نشود.
   - فقط آیتم‌های safe بازگردانی شوند؛ unsafe ها skip شوند.
   - در پایان، summary شامل rolled-back/skipped نمایش داده شود.

5. **بازگشت قابلیت ویرایش پس از rollback**
   - برای آیتم rollback‌شده، create/edit/delete پکیج دوباره فعال شود.
   - وضعیت آیتم از `sent_to_optimization` به `rolled_back_from_optimization` تغییر کند.

## سناریوهای الزامی فاز 12E-0 (Budget Scenario Semantics)

1. **تحلیل بودجه سناریومحور قبل از اجرای Optimization**
   - سناریو پیش‌فرض قبل از اجرا: `Minimum feasible budget`
   - کاربر باید بداند هر آیتم فقط یک‌بار در سناریو شمرده می‌شود و گزینه‌های جایگزین جمع نمی‌شوند.

2. **هشدار کمبود بودجه (غیر بلاک‌کننده)**
   - در صورت کسری بودجه، دیالوگ تصمیم‌گیری نمایش داده شود (نه توقف بی‌صدا یا اجرای بی‌صدا).
   - 3 گزینه قابل انتخاب باشند:
     - Optimize within current budget
     - Optimize all items and show financial shortage analysis
     - Cancel and update budget

3. **رفتار اجرای constrained**
   - خروجی شامل آیتم‌های deferred/excluded و خلاصه بودجه مصرفی/باقیمانده باشد.
   - انتخاب‌ها از بودجه موجود عبور نکنند.

4. **رفتار اجرای allow_shortage**
   - Optimization اجرا شود حتی اگر کسری وجود داشته باشد.
   - تحلیل کمبود مالی برای نتیجه/مدل تولید شود.

5. **تحلیل مالی هر مدل نتیجه**
   - برای هر proposal/result امکان مشاهده تحلیل مالی وجود داشته باشد.
   - تحلیل بر اساس گزینه‌های انتخاب‌شده همان مدل محاسبه شود.

6. **نمایش ارز صحیح**
   - نمایش نماد ارز برای IRR/USD/EUR/AED/CNY/TRY صحیح باشد.
   - نمایش اشتباه از جنس `$` برای همه ارزها قابل قبول نیست.

## سناریوهای الزامی فاز 12E-1 (Optimization Feasibility Diagnostics)

1. **تست هر دو مود اجرا**
   - یکبار `Optimize within current budget` اجرا شود.
   - یکبار `Optimize all items and show financial shortage analysis` اجرا شود.

2. **قاعده allow-shortage**
   - در مود allow-shortage، کمبود بودجه نباید علت بلاک‌کننده اجرا باشد.
   - اگر اجرای بهینه‌سازی شکست خورد، پیام باید علت غیر‌بودجه‌ای را با diagnostics نشان دهد.

3. **شفافیت علت شکست**
   - پیام شکست نباید صرفا بودجه/هزینه را حدس بزند.
   - باید مواردی مثل `no eligible candidates`، `missing coverage/dates` یا قیود عملیاتی را روشن کند.

4. **رفتار partial feasible**
   - اگر بعضی آیتم‌ها candidate معتبر دارند و بعضی ندارند، نتیجه partial تولید شود (وقتی all-or-nothing اجباری نیست).
   - آیتم‌های skipped/infeasible با دلیل قابل مشاهده باشند.

5. **تحلیل مالی در allow-shortage**
   - در صورت تولید نتیجه، تحلیل کمبود مالی برای proposal/result قابل مشاهده باشد.

## سناریوهای الزامی فاز 12E-2 (Scenario Consistency in Budget Analysis)

1. **یکپارچگی کامل سناریو**
   - با تغییر سناریو (`minimum_feasible` / `average_candidate` / `worst_case`) همه بخش‌ها همزمان تغییر کنند:
     - summary cards
     - charts
     - critical periods
     - period details
     - recommendations
     - narrative report

2. **عدم آمیختگی گزارش پیش‌فرض**
   - نباید فقط متن هدر سناریو تغییر کند و بدنه گزارش ثابت بماند.
   - بدنه باید از همان پاسخ سناریویی تولید شود.

3. **تحلیل مدل انتخابی**
   - در حالت `selected_optimization_result` تحلیل باید فقط از تصمیم‌های همان run/result ساخته شود.
   - روایت پایین صفحه باید عبارت `تحلیل مالی مدل انتخابی` را داشته باشد.

4. **سازگاری عددی**
   - مقدار بودجه موردنیاز بین هدر، کارت خلاصه، نمودار و جمع دوره‌ها هم‌خوان باشد (اختلاف فقط در rounding مجاز است).

5. **سازگاری تاریخ/زبان در UI فارسی**
   - برچسب دوره‌ها در نمودار/جدول در UI فارسی به Jalali نمایش داده شود.
   - گزارش سناریویی نباید دوباره متن Gregorian پیش‌فرض قدیمی را نمایش دهد.

## سناریوهای الزامی فاز 12E-3 (Deployment Binding + Optimizer Diagnostics)

1. **تایید اتصال صفحه به endpoint درست**
   - در UAT صفحه Budget Analysis باید از مسیر canonical سناریومحور تغذیه شود، نه endpoint قدیمی تصمیم‌ها.

2. **تایید به‌روزرسانی کامل با تغییر سناریو**
   - با تغییر سناریو، کارت‌ها/نمودار/جدول/گزارش روایی همزمان تغییر کنند و روی تحلیل پیش‌فرض قدیمی نمانند.

3. **تحلیل نتیجه انتخابی بهینه‌سازی**
   - در حالت selected result، گزارش باید مدل‌محور باشد و عبارت `تحلیل مالی مدل انتخابی` را نشان دهد.

4. **تشخیص رفتار مودهای بهینه‌سازی**
   - یک اجرای کنترلی برای CP-SAT و یک اجرای کنترلی برای GLOP انجام شود و تفاوت/عدم تفاوت خروجی‌ها ثبت گردد (بدون فرض باگ تا زمان اثبات).

5. **بازمحاسبه هزینه پس از تغییر محلی Proposal**
   - با حذف/ویرایش/افزودن آیتم در Proposal، مجموع هزینه و شمارش آیتم‌ها در UI باید فوری به‌روزرسانی شود.

## سناریوهای الزامی فاز 12E-4 (Financial Traceability Reconciliation)

1. **بومی‌سازی هشدار کسری بودجه**
   - در UI فارسی، دیالوگ کسری بودجه قبل از اجرا باید کاملا فارسی باشد و برچسب‌های انگلیسی نداشته باشد.

2. **تفکیک معنای هزینه‌ها**
   - در خروجی بهینه‌سازی، `Total Purchase Cost` و `Weighted Objective Cost` باید جداگانه نمایش داده شوند.
   - هزینه وزن‌دهی‌شده نباید به‌عنوان بودجه خرید واقعی تفسیر شود.

3. **سازگاری selected-result بین همه نماها**
   - برای یک `run_id` مشخص، مقدار بودجه موردنیاز در:
     - پنل مالی نتیجه
     - تب Budget Analysis در حالت `selected_result`
     باید یکسان باشد.

4. **سازگاری کارت ارز و معادل ریالی**
   - جمع ارز اصلی (USD/EUR/AED/CNY/TRY/IRR) باید با برچسب همان ارز نمایش داده شود.
   - معادل ریالی جدا و شفاف باشد؛ هیچ مبلغ ریالی با برچسب USD نمایش داده نشود.

5. **سازگاری تخصیص دوره‌ای**
   - اگر schedule پرداخت 30/70 وجود دارد، جمع دوره‌ها باید دقیقا برابر جمع کل خرید باشد.
   - تکرار مبلغ کامل در هر milestone قابل قبول نیست.

6. **Traceability**
   - در پاسخ تحلیل selected-result باید trace/reconciliation موجود باشد تا اختلاف احتمالی قابل ردیابی باشد.

## سناریوهای الزامی فاز 12E-4C (Financial UI Clarity + Narrative Restoration)

1. **بومی‌سازی کامل UI فارسی**
   - در صفحه Optimization و تحلیل مالی، متن‌های کاربرپسند باید کاملا فارسی باشند (به‌جز نام حل‌گرهایی مثل CP-SAT/GLOP/SCIP/CBC).

2. **شفافیت معنایی هزینه‌ها**
   - `هزینه کل خرید قابل اجرا` باید از `total_purchase_cost_irr` نمایش داده شود.
   - `هزینه هدف وزن‌دهی‌شده` باید جداگانه نمایش داده شود و به‌عنوان امتیاز داخلی حل‌گر تفسیر شود.
   - `بودجه مورد نیاز` باید با توضیح مبنای پرداخت/زمان‌بندی نمایش داده شود.

3. **یکپارچگی جدول اقلام انتخابی با جمع مالی**
   - جدول اقلام باید ستون‌های ارز اصلی، هزینه واحد/کل در ارز اصلی، نرخ تبدیل، معادل ریالی و پرداخت را داشته باشد.
   - جمع `معادل ریالی` جدول باید با هزینه خرید منتخب (در حد گردکردن) سازگار باشد.

4. **هشدار آشتی مالی به‌زبان کسب‌وکاری**
   - پیام اصلی اختلاف جمع‌های مالی باید قابل فهم برای کاربر کسب‌وکاری باشد.
   - جزئیات خام (diff/reasons/trace) فقط در بخش فنی تاشونده نمایش داده شود.

5. **بازگشت گزارش مدیریتی فارسی**
   - در تحلیل `selected_result` گزارش روایی باید با `📊 تحلیل مالی مدل انتخابی` شروع شود.
   - گزارش شامل جمع هزینه خرید، بودجه مورد نیاز/موجود، کسری/مازاد، جمع ارزی، دوره‌های بحرانی و اقدامات پیشنهادی باشد.
